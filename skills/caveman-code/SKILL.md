## МЕТОД ЧТЕНИЯ ЧУЖОГО КОДА (шаги, как канон)

1. **README первым** — цель проекта, установка, примеры использования,
   структура. Нет README → INSTALL/CONTRIBUTING/docs. Совсем нет — код
   личный, читать сложнее, будь готов.
2. **Каркас проекта**: `tree -L 2` (или find -maxdepth 2) — увидеть, где
   что лежит до чтения строк.
3. **ЗАПУСТИТЬ код и посмотреть, что делает** — входы/выходы, зависимости
   (towardsdatascience шаг 1: запусти и увидь).
4. **Точка входа** — main / точки старта, иди по главному пути исполнения.
5. **Вести по потоку** — вызовы, контрольные структуры, как данные текут.
6. **Выписать паттерны/стиль** — как обрабатывают ошибки, как именуют,
   как режут на функции/модули (барaнсель: паттерны впитываются от
   повторения, как словарный запас из книг).
7. **Читать КАЧЕСТВЕННОЕ** — высококачественные проекты (Linux kernel,
   awesome-codebases, официальные репозитории), не мусор: плохой код учит
   плохому (stackademic).

## АДАПТАЦИЯ ПРИМЕРА (не копипаст!)

- Copy-paste в теле = 1 из 4 посетителей SO копирует сниппет (Popper &
  Gibson) — но вставка вслепую = 15-40% багов от переноса.
- КАНОН АДАПТАЦИИ (AdaptivePaste): переименовать переменные под контекст,
  подогнать имена/границы/типы под СВОЙ код, понять смысл ПЕРЕД вставкой.
- При виде фичи — рассказать, какой пример/паттерн подсмотрен у индустрии
  (правило 21 канона: готовое раньше своего).
- Пример из доки лучше сниппета с форума: проверенный, актуальный, с
  объяснением "почему".

## СОВЕТЫ ПИСЬМА (свод индустрии, одобрено DataCamp/dev.to/Educative)

1. Имена читаемые: primes, а не x. Имя говорит ЗАЧЕМ.
2. Один стиль везде (отступы, пробелы, кавычки) — стиль-гайд + линтер.
3. Без «магических» чисел/строк — константы с именами (не 10, а MAX_ITEMS).
4. Модульность: одна функция = одно дело, файл 100-300 строк (канон файлов).
5. DRY (не повторяйся), KISS (проще — лучше), YAGNI (не строй на будущее),
   SOLID прагматично (одна причина меняться, завись от абстракций) —
   кодекс качества, закон 27 канона.
6. Комментарии — ПОЧЕМУ, а не ЧТО (хороший код объясняет себя сам:
   «хороший код читается как история» — baransel).
7. Тест до добавления: сначала доказать, потом писать (канон «тест до»).
8. Код читается больше, чем пишется: «Code is written once, read thousands
   times» (Educative) — пиши для читателя.

## ГРАБЛИ (не повторять)

1. Вставить сниппет вслепую → баги/несовместимость. Только понять +
   адаптировать (закон 26).
2. Писать с нуля то, что индустрия давно решила (канон «решена ли уже?») —
   сначала поиск готового, потом адаптация.
3. Читать плохой код для учёбы — учит плохому. Читай проверенное
   (awesome-codebases, официальные репо).
4. Переусложнение «на будущее» (YAGNI): пример допиливай под задачу,
   не добавляй лишнее.
5. Чужой путь/хардкод из примера не переносить в СВОЁ: адаптация = и пути,
   и переменные под контекст (канон путей: рантайм-переменные, не
   зашивать /home/... в код).

## ПРОВЕРКА ПЕРЕД ОТВЕТОМ (гейт)

- Я посмотрел, как это делает индустрия? (дока, пример, готовый код)
- Я назвал пример/паттерн, откуда взял? (правило 21)
- Пример адаптирован под контекст, а не вставлен как есть?
- Советы применены: имена, стиль, DRY, без магии?

Нет хотя бы одного — вернись к шагу 1, не отвечай с головы.
