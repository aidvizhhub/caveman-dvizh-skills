## НЕ ГАДАТЬ: локальные улики → потом веб (ОБЩЕЕ правило, канон авг 2026)

Источники: Google SRE Book (effective troubleshooting), Cisco 7-step methodology (PacketMentor), CompTIA 6-step, tgtechacademy IT methodology, runbook-гайды (upstat, incidenthub), JetBrains/VirtusLab (как писать правила для ИИ).

Порядок при ЛЮБОЙ проблеме (зависло, не работает, странно ведёт себя) — НЕ ГАДАТЬ:

**ШАГ 0 — определи проблему ТОЧНО (до всяких команд!):**
- Что именно сломано? (не «интернет сломан», а «X не может Y с 9:00»)
- Что изменилось? Ничто не ломается само: работало вчера — не работает сегодня = что-то поменялось. Найди изменение ПЕРВЫМ.
- Кого/что задевает? (один юзер / один сервис / всё)

**ШАГ 1 — улики ЛОКАЛЬНО (сначала, до всякого веба):**
- Логи: `journalctl -xe` (последние ошибки), `dmesg | tail -50`, `dmesg | grep -i "error\|fail\|hardware"`, логи сервисов (tail /tmp/*.log, ~/.local/state/*.log)
- Состояние: `ps aux | head -30`, `ss -tlnp`, `free -h`, `df -h`, `uptime`, `top -bn1 | head -20`
- ЖЕЛЕЗО (если подозрение на железо): `lscpu`, `lspci -nn`, `lsusb`, `smartctl -a /dev/sdX` (диск), `sensors` (температуры), `dmesg | grep -i "thermal\|usb\|pci\|ata\|i2c"`, `lshw -short | head -40`, `systemctl list-units --failed`
- Версии всего: `uname -a`, `cat /etc/os-release`, версии пакетов/ядра, `dmesg | head -5` (что за железо видит ядро)
- Скриншот/вывод ошибки целиком — это и есть «улика», с ней потом идти в веб
- КАНОН Cisco: команды нужны, чтобы ПОДТВЕРЖДАТЬ гипотезу, а не чтобы её придумывать. Не долбить show/ping наугад.

**ШАГ 2 — веб-ресёрч (camoufox.research или похожая, 10+ источников):**
- Узнать ТОЧНУЮ инфу про симптомы из улик
- Если проблема с НАШИМ ЖЕЛЕЗОМ: искать по модели железа (lscpu/lspci/lsusb дали модель) + симптом, например: «RTX 3070 зависает dmesg nvidia error», «NVMe slow SMART 0C», «AMD Ryzen 7000 usb disconnect»
- Сначала официальная документация/форум вендора (правило 9), потом issues/отзывы других (правило 13)

**ШАГ 3 — сопоставление и лечение:**
- Совпало: симптомы из локальных улик == известный баг в вебе → диагноз есть, вот фикс (прошивка, параметры ядра, RMA)
- НЕ совпало: улики указывают на софт/драйвер → лечить софт
- ОДНА переменная за раз (CompTIA): поменял одно → проверил → поменял следующее. Не менять 5 вещей одновременно — не поймёшь, что починило.
- Бэкап конфига ДО изменений, документировать результат (шаг 6 CompTIA обязателен): что было, что сделал, что помогло.
- Без улик в веб НЕ ходить — будешь гадать, а не диагностировать.

## FIX: MCP-тулы «Unknown tool» при прямом вызове (авг 2026) — РЕШЕНО

Причина НЕ в кэше сессии! В opencode v2 у MCP-серверов есть флаг `codemode`:
- По умолчанию `codemode: true` — тулы доступны ТОЛЬКО через Code Mode (execute-песочница, tools.camoufox.*).
- Прямой вызов (camoufox.ping) даёт «Unknown tool» — потому что тул не в нативном списке провайдера.

Лечение (проверено на практике):
1. В `~/.config/opencode/opencode.json` добавить серверу `"codemode": false`:
```json
"camoufox": {
  "type": "local",
  "codemode": false,
  "command": ["/home/<user>/.venvs/camoufox-research/bin/camoufox-research"]
}
```
2. Переподключить MCP через API:
```
opencode2 api POST /api/mcp/camoufox/disconnect
opencode2 api POST /api/mcp/camoufox/connect
```
3. ВАЖНО: имена тулов меняются с `camoufox.ping` на `camoufox_ping` (с подчёркиванием, префикс = имя сервера).
4. Текущая сессия подхватывает изменения ЖИВЬЁМ (каталог обновляется) — новая сессия НЕ нужна!
5. Признак успеха: `camoufox_ping` → pong, `camoufox_fetch_page` → текст страницы, `camoufox_web_search` → результаты.

Проверено: ping/fetch_page/web_search работают напрямую. Бэкап конфига: opencode.json.bak.

## FIX: camoufox «Connection closed» в opencode2 — зависший процесс MCP (23 авг 2026) — РЕШЕНО ✅

Симптом: `opencode2 mcp list` → `✗ camoufox failed: Connection closed`, тулы кауфми в сессии лежат. При этом САМ сервер жив: бинарь отвечает на запросы, а сервис opencode просто не пересоздаёт подключение.

Механика (по логам этой машины):
1. Сервис opencode спавнит процесс `/home/<user>/.venvs/camoufox-research/bin/camoufox-research`.
2. Если хоть один запрос завис >30с (у нас висли `resources/list` и `resources/templates/list` — `MCP error -32001: Request timed out`), сервис отдаёт таймаут, НО процесс остаётся жив и НЕ пересоздаётся (баг V2-сервиса: зависший процесс он не переживает, статус «closed» кэшируется навсегда).
3. Итог: `mcp list` вечно врёт «Connection closed» без единой попытки переподключения. Это НЕ значит, что кауфми сломан.

Диагностика (30 секунд, по порядку):
1. `opencode2 mcp list` — статус.
2. `ps aux | grep camoufox-research | grep -v grep` — есть живой процесс с 0:00 CPU, а тулы лежат = он завис (у нас: PID висел с 12:24, ответил на tools/list в 12:25, завис на ресурсах в 12:28).
3. `grep -E "mcp connected|failed to list MCP" ~/.local/share/opencode/log/opencode.log | tail` — «mcp connected … tools=48», потом «Request timed out» = диагноз подтверждён.
4. Прямая проверка сервера (отвечает за ~1с = лечится переподключением, не переустановкой):
   `printf '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"t","version":"1"}}}\n' | timeout 20 /home/<user>/.venvs/camoufox-research/bin/camoufox-research | head -c 200`

ЛЕЧЕНИЕ (без рестарта сервиса, текущую сессию не трогает):
1. Убить зависший процесс: `pgrep -f camoufox-research | xargs -r kill`
2. Переподключить через API: `opencode2 api post /api/mcp/camoufox/disconnect && opencode2 api post /api/mcp/camoufox/connect`
3. Проверить: `opencode2 mcp list` → `✓ camoufox connected`

Если не помогло — последний рубеж: `opencode2 service restart` (перезапустит и текущую сессию).

Один-лайнер на всё:
```
pgrep -f camoufox-research | xargs -r kill; opencode2 api post /api/mcp/camoufox/disconnect && opencode2 api post /api/mcp/camoufox/connect && opencode2 mcp list
```

Замечание: в stderr сервера есть косметический warning pydantic — `Field 'lifespan' has an incomplete definition` (pydantic-settings 2.15 + mcp 1.29.0). На работу НЕ влияет, игнорировать.

Проверено на этой машине (23 авг 2026): зависший процесс убит → disconnect/connect → `✓ camoufox connected` ✅; сервис НЕ перезапускался, текущая сессия не пострадала ✅; все 48 тулов + 4 ресурса + 3 промпта отвечают мгновенно ✅.

## FIX: Firefox плеер не работает, а интернет есть (авг 2026) — РЕШЕНО

Симптом: видео не играет / чёрный экран / крутится, а скорость есть. Чаще всего виноват НЕ интернет!

Диагноз ОДНОЙ командой (канон):
```bash
firefox --version; rpm -q ffmpeg; find /usr/lib64 ~/.mozilla/firefox -iname '*widevine*' | head; lspci | grep -i vga
```
- ffmpeg есть + GPU есть + Widevine НЕ найден → DRM-видео (YouTube, Kinopoisk, Netflix, онлайн-кинотеатры) не играет. Widevine = модуль для защищённого видео, без него никак.

Фикс (оптимальный, 3 шага):
1. Найти АКТИВНЫЙ профиль: `ls -la ~/.mozilla/firefox/*/.parentlock` — у кого дата СЕГОДНЯ, тот и живой (профилей бывает несколько!).
2. Вписать user.js при закрытом Firefox (user.js сильнее prefs.js и не перезатрётся):
```bash
printf 'user_pref("media.eme.enabled", true);\nuser_pref("media.gmp-widevinecdm.enabled", true);\nuser_pref("media.gmp-widevinecdm.visible", true);\n' > ~/.mozilla/firefox/<ПРОФИЛЬ>/user.js
```
3. Перезапуск: pkill ОТДЕЛЬНЫМ вызовом (правило 11, `fire[f]ox`) → запуск с env из живого GUI-процесса:
```bash
GPS=$(pgrep -f 'gnome-s[h]ell' | head -1); export $(tr '\0' '\n' < /proc/$GPS/environ | grep -E '^(DISPLAY|WAYLAND_DISPLAY|XAUTHORITY|XDG_RUNTIME_DIR)=' | tr '\n' ' '); nohup firefox > /tmp/firefox.log 2>&1 &
```

ВАЖНО: Widevine скачивается САМ при первом открытии DRM-сайта (YouTube) — пустая папка gmp-widevinecdm сразу после старта = НОРМА, не паниковать. Проверка: about:addons → Плагины → Widevine Content Decryption Module.

Если не помогло (по убыванию вероятности): расширения-блокировщики (Режим устранения неполадок) → отключить аппаратное ускорение (Настройки → Основные → Performance; на NVIDIA глючит) → очистить кэш → Refresh Firefox.

ОБЩИЙ УРОК (на все GUI-приложения): перезапуск GUI-программы из CLI-сессии = env (DISPLAY/WAYLAND/XAUTHORITY/XDG_RUNTIME_DIR) берём из `/proc/<PID>/environ` живого GUI-процесса (gnome-shell), export, запуск в фон с логом. Настройки GUI без UI правим через user.js/prefs.js при закрытом приложении + перезапуск — это «1 клик» для любой похожей беды.
